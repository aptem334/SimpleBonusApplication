# T-010 — «Мёртвая зона» мелких покупок: бонус и комиссия обнуляются

**Status:** done
**Priority:** medium
**Component:** state

## Контекст
Вскрыто при перепроверке T-008 на живом приложении, 30.09.2026.

Правило «покупки меньше 20 ₽ — комиссия 10%» и правило «Shop — 10% бонусов»
применяют один и тот же процент. Для сумм от 0.01 до 0.04 результат округляется
до `0.00` для обоих.

Проверено расчётом:

| Сумма | `amount × 10%` | Бонус | Комиссия |
|---|---|---|---|
| 0.01 | 0.001 | 0.00 | 0.00 |
| 0.04 | 0.004 | 0.00 | 0.00 |
| 0.05 | 0.005 | 0.01 | 0.01 |

Наблюдаемое поведение сервиса:

```
GET /api/payment/Shop/0.005  →  200  money 100000.00 → 99999.99  бонус 0.00  комиссия 0.00
GET /api/payment/Shop/0.01   →  200  money 99999.99  → 99999.98  бонус 0.00  комиссия 0.00
```

## Почему это дефект, а не мелочь

1. **Деньги списываются, пользы нет ни одной стороне.** Клиент потерял копейку,
   банк не получил комиссию, клиент не получил бонус. Запись в `transactions` создаётся.
2. **Правило формально соблюдено, фактически не исполнено.** Код считает 10% и
   получает ноль. Кто будет читать лог и увидит `commission=0.00` при `amount<20` —
   решит, что сломался расчёт.
3. **Асимметрия.** Для 19.99 комиссия округляется **вверх** (1.999 → 2.00) — банку выгодно.
   Для 0.01 — **вниз** (0.001 → 0.00) — банку невыгодно. Одно правило округления
   (`HALF_UP`) даёт разный эффект в зависимости от масштаба суммы.

## Требование
Определить и зафиксировать минимальную допустимую сумму покупки.
Согласовано с T-008 (вопрос о минимальной сумме один и тот же).

Предлагаемое техническое значение — **0.05 ₽**: это наименьшая сумма, при которой
и бонус, и комиссия ненулевые. Значение ниже — это плата в никуда.

## Критерии приёмки
- [ ] Решение согласовано с T-008
- [ ] Минимальная сумма задаётся в конфиге, а не зашита в код
- [ ] Сумма ниже минимума → 400 с внятным описанием
- [ ] В сценарной таблице `docs/DOMAIN.md` есть строка с границей
- [ ] Тест на границу: чуть ниже → 400, ровно граница → 200
- [ ] `./mvnw clean verify` зелёный

## Решение / резолюция
**Принято 0.10 ₽.** Заказчик выбрал это значение явно.

Сделано:
- `AppRulesProperties` (record, `@ConfigurationProperties("app")`) с полем `minAmount`
- `application.yml` → `app.min-amount: "0.10"`
- Проверка минимума в `InitPaymentState`, **после** проверки знака
- Тесты: `PaymentApiTest$MinimumAmount` (8 тестов) + строка `Shop 0.10` в сценарной таблице
- `docs/DOMAIN.md` дополнен разделом о минимальной сумме

Итого 73 теста, `BUILD SUCCESS`. Проверено на живом сервисе:

```
Shop 0.01  → 400  Сумма покупки меньше минимальной: 0.01, минимум 0.10
Shop 0.09  → 400  Сумма покупки меньше минимальной: 0.09, минимум 0.10
Shop 0.10  → 200  бонус 0.01, комиссия 0.01
```

### Найдено по ходу

**Баг: YAML терял хвостовой ноль.** Тест поймал, что в сообщении выводилось
`минимум 0.1` вместо `минимум 0.10`. Причина: YAML разбирает `0.10` как double,
а `Double.toString(0.10)` возвращает `"0.1"`. Значение теряло точность ещё при
чтении конфига, задолго до расчётов.

Исправлено в двух местах:
1. Кавычки в YAML (`min-amount: "0.10"`) — YAML отдаёт строку.
2. `setScale(Money.SCALE)` в конструкторе record'а — инвариант держится,
   откуда бы значение ни пришло.

Второй пункт важнее первого: он убирает класс ошибок целиком, а не один случай.

### Порядок проверок

Знак проверяется раньше минимума. Изначально было наоборот — чтобы сумма `0.001`
не отвергалась текстом про `0.00`. Но тогда `-5.00` отвергалась бы как
«меньше минимальной», что теряет информацию. Отрицательное значение — это
другая ошибка, и называть её надо прямо.

Побочный эффект принят осознанно и зафиксирован в DOMAIN.md: суб-копеечные
суммы по-прежнему отвергаются с текстом про `0.00`. Это следствие решения
округлять сумму на входе, сам вопрос открыт в T-008.
