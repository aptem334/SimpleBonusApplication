# AGENTS.md — рабочий контракт для агентов

Этот файл — **единственный источник правил** для любого агента (или человека), который работает с проектом.
Если правило есть здесь — оно обязательно. Если правила нет — его нужно либо выполнить по смыслу, либо оформить тикетом.

---

## 0. Железное правило

> **Никогда не меняй доменные правила молча.**

Проценты (10 / 17 / 30), пороги (20 / 300) и формулы — это **бизнес-требование**, а не деталь реализации.
Если кажется, что правило «нелогичное» или «ошибочное» — **заведи тикет с вопросом**, не правь код.

Пример: нельзя просто написать `if (amount > 300) bonus = amount * 0.30` в обход State-паттерна,
потому что «так короче». Сначала — тикет, потом — обсуждение.

## 1. Команды

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 25)

./mvnw clean verify        # полная сборка + все тесты  (главная проверка)
./mvnw test                # только тесты
./mvnw -Dtest=ClassName test    # один тест-класс
./mvnw spring-boot:run     # поднять приложение на :8080
```

База данных — **H2 в памяти**, схема создаётся автоматически. Ничего ставить не нужно.

## 2. Структура проекта

```
src/main/java/com/bank/bonus/
├── BonusServiceApplication.java   точка входа
├── controller/    REST-контроллеры, маппинг HTTP → вызовы сервиса. Без бизнес-логики.
├── service/       оркестрация: что делать, в каком порядке, транзакции
├── processor/     PaymentProcessor — прогоняет платёж по цепочке состояний (State)
├── state/         конкретные состояния платежа. ОДНО состояние = ОДНО правило.
├── model/         JPA-сущности и enum'ы
├── repository/    Spring Data JPA — доступ к БД
├── config/        конфигурация Spring
└── exception/     свои исключения + маппинг на HTTP-коды
```

**Правило слоёв:** `controller → service → processor/state → repository`.
Слой **не пропускает** соседний слой. `controller` не ходит в `repository`. `state` не ходит в `controller`.

## 3. Доменные правила (краткая версия)

Полная версия с таблицами переходов — в [`docs/DOMAIN.md`](docs/DOMAIN.md). Это **source of truth**.

| Условие | Результат |
|---|---|
| Покупка в `Shop` | +10% бонусов |
| Покупка в `Online` | +17% бонусов |
| `amount > 300` | +30% бонусов (**вместо** обычных 10/17) |
| `amount < 20` | −10% комиссия в пользу банка |
| Денег на счёте меньше суммы | HTTP 400, платёж не проходит |
| Сумма ≤ 0 или не число | HTTP 400 |

## 4. Соглашения по коду

- `BigDecimal` для денег. **Никогда** `double`/`float`.
- Деньги округляются до **2 знаков** `RoundingMode.HALF_UP`. Точки — `%` и пороги.
- Пакеты в lowercase. Классы — CamelCase. Методы — camelCase.
- Состояния в `state/` реализуют общий интерфейс `PaymentState`.
- Каждое новое правило = новое состояние, а не `if` в существующем.
- Комментарии объясняют **почему**, а не **что**.

## 5. Цикл работы с тикетом

Агент берёт тикет и проходит цикл. Не перескакивать шаги.

```
1. ПРОЧИТАТЬ   tickets/<id>.md — понять что именно нужно
2. РЕАЛИЗОВАТЬ  минимальный код, закрывающий требование
3. ТЕСТ         тест, который ПАДАЕТ без этого кода и ПРОХОДИТ с ним
4. ПРОВЕРИТЬ    ./mvnw clean verify  → зелёное?
5. ЕСЛИ КРАСНОЕ:
     а) прочитать вывод теста
     б) если это дефект кода       → починить (шаг 2)
        если это новое требование  → завести НОВЫЙ тикет
        если это неоднозначность   → завести тикет с вопросом
6. ЗАКРЫТЬ      в тикете поставить Status: done, описать что сделано
```

**Тест должен падать до реализации.** Тест, который проходит всегда, хуже отсутствия теста:
он создаёт ложное ощущение защищённости. Если не можешь заставить тест упасть — тест неверен.

---

## 6. Формат тикета

Файл в `tickets/`, имя — номер и короткий слаг: `T-001-bootstrap.md`.

```markdown
# T-001 — Краткое название

**Status:** todo | in-progress | done | question
**Priority:** high | medium | low
**Component:** controller | service | processor | state | model | infra | docs

## Контекст
Почему это нужно. 2–5 предложений.

## Требование
Что конкретно должно стать правдой. Проверяемое утверждение.

## Критерии приёмки
- [ ] ...
- [ ] `./mvnw clean verify` зелёный

## Решение / резолюция
(заполняется при закрытии)
```

**`Status: question`** — когда требование неоднозначно. Это нормальный и желательный ход:
лучше остановиться и спросить, чем угадать и заложить неверную логику в тест.

## 7. Что делать, если сборка красная

1. Прочитать **первое** осмысленное сообщение об ошибке, а не последнее.
2. Если непонятно — убрать `--quiet`, запустить `./mvnw clean verify` целиком.
3. Зафиксировать находку тикетом **до** того, как починить, если это не тривиально.
4. Никогда не «лечить» сборку удалением теста или ослаблением проверки.
   Ослабление проверки — это не починка, а сокрытие дефекта.
